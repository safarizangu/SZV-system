# Phase 6 — UI/UX Audit

Safari Zangu Ventures booking system — responsive/UI audit of the public site, admin panel, and agent portal at `http://localhost/safari-zangu`.

**Method:** Python Playwright (Chromium headless), scripted navigation + login, full-page screenshots at 5 breakpoints (1440×900, 768×1024, 390×844, 375×812, 320×568), plus `page.evaluate()` measurements of `document.documentElement.scrollWidth` vs viewport width (overflow detection), `getBoundingClientRect()` on `.admin-btn`/`button` elements (touch-target sizing), and DOM queries for `.admin-table-wrap` coverage. Hamburger menus were actually clicked and the open state captured. One modal (Add Lead) was triggered and captured. All screenshots are under `screenshots/uiux/`, named `<page-slug>_<width>.png` (e.g. `admin-leads_390.png`), with `-nav-open` and `-modal` suffix variants where applicable.

**Login verified:** both admin (`qa_audit_bot`) and agent (`qa_audit_agent`) sessions authenticated successfully (confirmed via post-login redirect URL away from the login page) and were logged out again at the end of each capture run.

**Pages covered:** Homepage (`/`, incl. `#customize` custom-safari form), Packages (`/packages.php`), a package detail/booking page (`/book.php?package_id=1`), Contact (`/contact.php`), Booking tracking (`/track.php`); Admin Dashboard/Leads/Quotations/Bookings/Customers/Analytics (`admin/index.php`, `leads.php`, `quotations.php`, `bookings.php`, `customers.php`, `analytics.php`); Agent Dashboard/Leads/Commissions (`agent-portal/index.php`, `leads.php`, `commissions.php`). Three additional admin pages (`quotation_new.php`, `package_edit.php`, `operations_calendar.php`) were spot-checked at mobile widths specifically to verify the `.admin-table-wrap` pattern, since a code search flagged them as the only admin pages with a `<table>` and no wrap class.

A note on method integrity: an early full-page capture of the homepage at 768px/320px appeared to show large blank gaps mid-page. Before reporting this as a bug I verified it with `getComputedStyle` (opacity:1, visibility:visible, display:block on every section pre-scroll) and by re-capturing after dispatching real incremental `window.scrollTo()` events — the content rendered correctly. This was a headless full-page-screenshot paint-timing artifact (large image-heavy page, single-pass capture), not a site defect, and is **not** reported as a finding. All homepage screenshots in this report were taken with the scroll-settle fix applied.

## Findings

### F1 — Homepage CTA button causes real horizontal page overflow at 320–375px
**Severity:** Medium
**Impact:** The page scrolls horizontally on narrow phones (confirmed `document.documentElement.scrollWidth` = 382px against a 320px and 375px viewport — 62px and 7px of overflow respectively). Users can accidentally pan the page sideways instead of only scrolling down; the layout reads as unfinished/broken on the most common small-phone widths.
**Risk:** First impression of the marketing site on the devices most safari shoppers actually browse on (phones). Low-to-moderate business risk but highly visible.
**Root cause:** Confirmed via `getBoundingClientRect()` — the offending element is the `<a class="btn-sz-dark">View All Packages & Full Itineraries</a>` link in the packages section. `.btn-sz-dark` (shared with `.btn-sz-primary/.btn-sz-outline/.btn-sz-ghost`) is defined with `white-space: nowrap` and fixed `padding: 0.8rem 2rem` and no `max-width`/responsive text handling. Unlike the CTA-banner's buttons at the bottom of the page (`.cta-banner-actions .btn-sz-dark`, which do get a `width:100%; max-width:300px` override inside the `@media (max-width:480px)` block), this particular button on the packages section has no such override, so its long label is forced onto one line and bursts out of its 320/375px-wide container.
**File location:** `assets/css/main.css` lines 412–432 (base button rule, `white-space: nowrap`); no mobile override exists for this specific instance. Markup: `views/home.php` line 299 (`<a href="...packages.php" class="btn-sz-dark">View All Packages & Full Itineraries</a>`).
**Recommended fix:** Add the button text to the existing mobile button-shrink pattern already used elsewhere on the page (e.g. give the containing `<div class="text-center mt-5 fade-in">` a mobile rule that sets `width:100%; max-width: 320px` and allows `white-space: normal` on its `.btn-sz-dark` child below ~480px, matching the fix already applied to the CTA banner's buttons).
**Evidence:** `screenshots/uiux/home_320.png`, `screenshots/uiux/home_375.png` (same bug visible via `screenshots/uiux/custom-safari-form_320.png` / `_375.png`, captured from the same page).

### F2 — Admin dashboard grid overflows the viewport by ~20px at 1440px desktop width
**Severity:** Medium
**Impact:** At 1440×900 (a very common laptop resolution and one of the five breakpoints in scope), `document.documentElement.scrollWidth` = 1460px vs a 1440px viewport, producing an unwanted horizontal scrollbar on the main admin dashboard. Not catastrophic, but unprofessional on the admin's primary daily-use screen.
**Risk:** Admin staff use this page constantly; a spurious horizontal scrollbar is a persistent small irritant and signals an unpolished panel to anyone reviewing the system (e.g. a client demo on a laptop).
**Root cause:** `admin/index.php` (lines 84 and 258) lays out the dashboard with an inline `style="display:grid;grid-template-columns:1.3fr 1fr;gap:1.25rem;align-items:start"` (class `admin-split-layout`). The codebase already has a documented fix for exactly this failure mode — grid items default to `min-width:auto`, so a `.admin-table` with its base `min-width:500px` (admin.css line 425) can force its grid column wider than the column's fair share — but that fix, `div[style*="display:grid"] > * { min-width: 0; }`, is scoped only inside `@media (max-width: 1024px)` (admin/css/admin.css line 758). It is never applied at desktop widths, so the exact bug it was written to prevent recurs above 1024px. At 1440px the 1fr column's fair share works out to roughly 485px (1440 − 240px sidebar − 2×32px content padding − 20px grid gap, split 1.3:1), just under the table's hard 500px floor, so the column — and the page — is pushed ~20px wider than the viewport.
**File location:** `admin/css/admin.css` line 758 (fix scoped to the wrong media query) and line 425 (`.admin-table { min-width: 500px; }`); markup at `admin/index.php` lines 84, 258.
**Recommended fix:** Move (or duplicate) the `div[style*="display:grid"] > * { min-width: 0; }` rule outside the `@media (max-width:1024px)` block so it applies at all widths, not just ≤1024px.
**Evidence:** `screenshots/uiux/admin-dashboard_1440.png` (overflow is a few pixels and not obviously visible in a static screenshot, but confirmed programmatically and reproducible by checking the scrollbar at 1440px).

### F3 — Inconsistent `.admin-table-wrap` usage across admin pages (code-level consistency gap)
**Severity:** Low
**Impact:** Of the admin tables checked, 4 of 38 `<table>` instances in the `admin/` directory do not use the project's own `.admin-table-wrap` horizontal-scroll pattern:
- `admin/analytics.php` lines 289, 322, 345 — three `<table class="admin-table" style="min-width:0">`, explicitly overriding the component's default `min-width:500px` instead of wrapping. (The 4th table on the same page, lines 536–537, correctly uses `.admin-table-wrap`.)
- `admin/quotation_new.php` line 824 and `admin/package_edit.php` line 667 — raw `<table style="width:100%;font-size:.85rem;...">`, not even using the `.admin-table` class, and no wrap.
- `admin/operations_calendar.php` line 239 — wrapped in a hand-rolled `<div style="overflow-x:auto;margin-bottom:1.25rem">` instead of the standard `.admin-table-wrap` class, with an explicit `min-width:640px` on the table forcing scroll.

I verified this does **not** currently cause a visible layout break at the tested breakpoints: `admin-analytics_320/375/390.png` and `admin-quotation-new_320/390.png` / `admin-package-edit_320/390.png` all show `hasOverflow:false` (no page-level horizontal scroll), because these particular tables happen to have few/short columns, and the site-wide mobile rule `.admin-table { zoom: .4; }` (admin.css line 925, ≤480px) shrinks all tables — wrapped or not — to the same ~40% visual scale, so the three un-wrapped Analytics tables are not noticeably less legible than the correctly-wrapped ones in a side-by-side comparison I ran. The risk is forward-looking rather than active today: these tables have no safety net if their content grows (more event types, more line items in a quotation), where the wrapped tables would simply scroll and the un-wrapped ones would either overflow the page or (for the `min-width:0` analytics case) squeeze indefinitely.
**Root cause:** Pattern not applied consistently when these specific pages/tables were built, despite 34 other locations across the admin panel doing it correctly.
**File location:** `admin/analytics.php:289,322,345`; `admin/quotation_new.php:824`; `admin/package_edit.php:667`; `admin/operations_calendar.php:239`.
**Recommended fix:** Wrap all four locations in `<div class="admin-table-wrap">…</div>` per the established pattern, and drop the ad-hoc `style="min-width:0"` / inline `overflow-x:auto` divs in favor of it, for consistency and future-proofing.
**Evidence:** `screenshots/uiux/admin-analytics_390.png`, `_320.png`; `screenshots/uiux/admin-quotation-new_320.png`, `screenshots/uiux/admin-package-edit_320.png`; `screenshots/uiux/admin-operations-calendar_390.png` (table only renders when a calendar day is selected via `?day=`, so it did not appear in this capture — confirmed by code inspection instead).

### F4 — `.admin-table { zoom: .4 }` mobile fallback produces small text, by deliberate design
**Severity:** Low
**Impact:** Below 480px, every `.admin-table` (leads, quotations, bookings, customers, analytics) is rendered at 40% visual scale (computed: base `font-size:.8rem`/12.8px × zoom 0.4 ≈ 5px nominal, though Chromium's effective on-screen glyph size in my cropped-element screenshots reads closer to a compact-but-legible size in practice — see evidence). The code comment above this rule (admin.css lines 914–924) explicitly documents this as an intentional trade-off ("Reading or tapping a specific cell is then a pinch-zoom away") rather than an oversight, and correctly notes the Firefox fallback (where `zoom` is unsupported) reverts to normal size + `.admin-table-wrap`'s horizontal scroll.
**Risk:** Low — this is a conscious, documented design decision with a working fallback path, not a defect. Flagging it per the audit brief's instruction to check mobile table usability; it is a genuine usability trade-off (small text/tap targets inside the zoomed table) worth the team re-confirming is acceptable for their actual field-agent usage, but it is not a bug to "fix" blindly.
**File location:** `admin/css/admin.css` lines 895–925 (the `@media (max-width:480px)` block, specifically line 925 `.admin-table { zoom: .4; }`).
**Evidence:** `screenshots/uiux/admin-leads_320.png`, `screenshots/uiux/admin-customers_320.png`, `screenshots/uiux/admin-bookings_320.png` show the shrunk-but-functional table rendering described above.

### F5 — Admin/agent `.admin-btn` touch targets measure 40×40px on mobile, 4px under the 44px guideline
**Severity:** Low
**Impact:** Every `.admin-btn` (and `button.admin-btn`) measured across admin and agent pages at 390/375/320px — Search, +Add Lead, +New Quotation, +New Lead, View All, Gallery, Itineraries, Packages, Commissions, Edit Profile — consistently measures height 40px via `getBoundingClientRect()`. This is 4px short of the commonly cited 44×44px (WCAG 2.5.5 AAA / Apple HIG) minimum touch target.
**Risk:** Minor — 40px is still comfortably tappable for most users and this was a deliberate improvement (see below), not a regression.
**Root cause:** `admin/css/admin.css` line 904, inside `@media (max-width:480px)`: `.admin-btn { min-height: 40px; padding: .5rem .85rem; }`. The preceding code comment (lines 902–903) states this value replaced an earlier version that shrank font/padding with no minimum at all, i.e. it is a known, already-improved value, just not quite at the 44px mark.
**File location:** `admin/css/admin.css` line 904.
**Recommended fix:** Bump `min-height` from `40px` to `44px` in that rule for full compliance with the touch-target guideline; low effort, no layout risk since it was already being explicitly sized.
**Evidence:** Measured programmatically across `admin-dashboard_390.png`, `admin-leads_390.png`, `admin-quotations_390.png`, `admin-bookings_390.png`, `admin-customers_390.png`, `agent-dashboard_390.png`, `agent-leads_390.png` (all buttons measured h=40px).

### F6 — `packages.php` has a negligible (~5px) horizontal overflow at 320px
**Severity:** Low
**Impact:** `document.documentElement.scrollWidth` = 325px vs a 320px viewport. Visually imperceptible in the screenshot; flagged for completeness since the audit brief asks for overflow measurement at every breakpoint.
**Root cause:** The package-section heading/intro block (`.pkg-section-header`, `h2.display-2`, intro `<p>`) computes to 308px wide inside an 18px-offset container at the 320px viewport, a few px past the available width — likely a sub-pixel/line-height rounding effect rather than a structural layout bug (no single element was found grossly oversized the way F1's button was).
**File location:** Section container around `views/packages.php`'s package listing header; exact selector not pinned down further given the small magnitude (5px) did not justify deeper tracing relative to the higher-severity findings above.
**Evidence:** `screenshots/uiux/packages_320.png`.

## What worked well (positive findings, for balance)

- **Mobile navigation is implemented and functional everywhere it's needed.** The public site (`#nav-toggle` / `#mobile-nav`), the admin panel (`#adminHamburger` / `.admin-sidebar`), and the agent portal (`#agentHamburger` / `.agent-nav-links`) were each clicked programmatically and confirmed to open with the expected content visible — see `screenshots/uiux/home-nav-open_390.png`, `screenshots/uiux/admin-dashboard-nav-open_390.png`, `screenshots/uiux/agent-dashboard-nav-open_390.png`. The agent portal even has a documented, deliberate fix (agent.css lines 128–132) for a previously-reported issue where the standalone Sign Out link got pushed off-screen at narrow widths — it's now folded into the dropdown instead, and this was confirmed working.
- **34 of 38 admin tables correctly use `.admin-table-wrap`** and scroll horizontally rather than breaking page layout — confirmed with `hasWrap:true` across Leads, Quotations, Bookings, Customers, and the agent portal's Leads/Commissions/Dashboard tables at every breakpoint from 1440px down to 320px, with zero page-level overflow detected on any of those pages.
- **The agent portal deliberately reuses admin.css's component classes** (`.admin-card`, `.admin-btn`, `.admin-table`, `.admin-modal`, `.badge-status`) rather than reinventing them (documented at the top of `agent-portal/css/agent.css`), which is why its responsive behavior is as solid as the admin panel's.
- **The "Add Lead" modal** (admin/leads.php) was triggered and captured at 390px (`screenshots/uiux/admin-leads-modal_390.png`): it renders as a proper full-width sheet, fields stack cleanly with labels, and the close control is present and reachable — no overflow, no clipped fields.
- **Contact, Track, and Package-detail/booking pages had zero measured overflow at any of the 5 breakpoints** and read cleanly in every screenshot (`screenshots/uiux/contact_*.png`, `track_*.png`, `package-detail_*.png`).
- **The itinerary/quotation "three side-by-side panels" tablet-collapse fix** (admin.css lines 762–775, stacking `.day-resource-grid` to 1 column at ≤1024px instead of the generic ≤768px breakpoint) and the **flex-wrap auto-fix for inline button toolbars** (admin.css lines 866–881) are both examples of the team proactively fixing real overflow bugs they found live — good practice, and neither reintroduced a regression in this audit's captures.

## Overall UI/UX Assessment

The responsive foundation here is genuinely solid for a system of this size: a consistent design-token system, a documented component library (`.admin-btn`, `.admin-table`/`.admin-table-wrap`, `.admin-card`, `.admin-modal`), hamburger navigation implemented correctly across all three surfaces (public, admin, agent), and clear evidence in the CSS comments themselves of a team that has already hunted down and fixed several real mobile bugs (the itinerary tablet-collapse, the agent sign-out overflow, the inline-flex-toolbar wrap rule). That history of self-correction is a good sign for maintainability.

The gaps found in this pass are narrow and traceable rather than systemic: one marketing-page CTA button (F1) and one admin dashboard grid (F2) have a confirmed, reproducible overflow with a clear one-line root cause each — both are quick, low-risk fixes because the surrounding pattern (responsive button overrides, the grid min-width:0 fix) already exists elsewhere in the codebase and just needs to be extended to cover these two cases. The table-wrap inconsistency (F3) and the 40px vs. 44px touch target (F5) are minor hygiene items, not active breakage. The 40%-zoom mobile table fallback (F4) is a legitimate design trade-off that the team made consciously and documented — worth a product decision on whether it's still the right call for field use, but not a defect.

No critical or high-severity issues were found: nothing blocks task completion, nothing hides functionality, and no page was unusable at any tested breakpoint. The two Medium findings (F1, F2) are the ones worth prioritizing — both are visible, both are cheap to fix given the existing patterns, and F1 in particular affects the public marketing site's first impression on phones, which is the highest-traffic surface for a tour operator's booking funnel.
